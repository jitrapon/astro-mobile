## 1. Overview

Software-composition analysis on the Gradle dependency graph is currently post-merge only. The job that feeds GitHub's Dependency Graph runs on push, so it produces alerts after a vulnerable dependency has already landed on `main`; the pull-request vulnerability scan has no lockfile or SBOM to read and so scans nothing of the Gradle graph. A PR can therefore introduce a known-vulnerable dependency, pass every security check, and surface only afterwards as an alert. This branch closes that window by generating a machine-readable bill of materials from the resolved Gradle graph at PR time and scanning it as a blocking gate.

## 2. Objective

A pull request that adds or upgrades a Gradle dependency carrying a `high`-or-worse advisory fails CI before merge, rather than being reported after it. The existing post-merge dependency-inventory job keeps working as the Dependency Graph / Renovate alert channel.

## 3. Requirements & Context

**Acceptance criteria** (from the issue):

- A PR-time job generates a CycloneDX or SPDX SBOM from the **resolved** Gradle dependency graph and runs the vulnerability scanner against that artifact.
- The gate is **blocking**: `high` and above advisories fail the PR.
- The post-merge `dependency-submission` job is **retained** as the inventory channel feeding Dependency Graph and Renovate — it is not replaced by this gate, and the gate is not bolted onto it.
- The existing `osv-scanner` ignore-list semantics carry over, so an accepted advisory stays accepted.

**Constraints and scope notes:**

- The trigger for this work has fired: the first real product dependencies (Ktor client, kotlinx.serialization, kotlinx.coroutines, Koin, and their test-only counterparts) landed with M-1 part 2 and did not bring the gate with them. The dependency surface now churns, which is what the gate was waiting on.
- The two candidate approaches named in the issue are committed Gradle dependency lockfiles **or** SBOM generation from the resolved graph. The issue's recommendation and acceptance criteria both settle on the SBOM route; lockfiles are the rejected alternative.
- Adding an SBOM generator means adding and pinning a new build plugin. Its multiplatform support is imperfect — the resolved graph spans Android, JVM, and three Kotlin/Native iOS targets — so which configurations are resolved, and whether a native or test-only configuration can be resolved at all on the CI runner, is the load-bearing unknown.
- This is CI and build-tooling work. It must not change product dependencies, product code, or the Kotlin/Swift lint toolchains.
- The gate runs on the host-portable CI half; it must not add work to the macOS runner, whose per-minute cost is the reason the CI split exists.
- The repository's convention is that new dependency versions are declared in the Gradle version catalog rather than inline, and that GitHub Actions are SHA-pinned. Both apply to whatever this branch adds.
- Verification tasks wired into the aggregate local gate are subject to the partition drift guard and must be classified into one of the two CI halves. Whether this gate belongs inside that aggregate or alongside it as a CI-only artifact step is a decision this branch has to make deliberately.

**Prior art:** this finding was deferred from the adversarial review of the M-1 scaffold branch. The reasons for deferring were scope (it was an edge in an earlier fix, not a new defect), rarity (the scaffold's dependency set was frozen and standard), and proportionality (an SBOM pipeline is disproportionate for a scaffold). None of those still hold.

## 4. Implementation Plan and Progress Tracking (for agent)

The gate is assembled bottom-up: prove an SBOM can be produced from this KMP graph at all, prove `osv-scanner` actually parses it, make the path fail-closed and self-testing, then wire it into CI and prove it blocks.

- [x] 1. Add a CycloneDX SBOM generator to the build: pin its version in `gradle/libs.versions.toml` (new `[versions]` + `[plugins]` entries, never inline). Write down the concrete aggregation wiring rather than assuming it — name whether the generator is applied to the root and told to traverse subprojects, or applied per-module with the outputs merged, and which task produces the single artifact CI scans. Change no product dependency. Do **not** wire the task into `check`: SBOM generation produces an artifact, which is coverage beyond `check` — the same classification the repo already gives `:androidApp:assemble` and `:shared:linkReleaseFrameworkIosArm64`.
- [x] 2. Scope the SBOM to **every configuration that resolves a Maven coordinate this repo can remediate**: no allow-list at all (`includeConfigs` empty, so a new target/source set/module widens the BOM automatically), and a skip list carrying only the dependencies this repo has no way to act on. Those are the buildscript `classpath` — the same `^classpath$` exclusion `dependency-submission` applies, and for the same reason: AGP's build-time tooling never ships and its advisories are unremediable here — **plus the equivalent tooling AGP plants on _project_ configurations**, which the buildscript filter does not reach: `androidLintTool` (Bouncy Castle) and `unified-test-platform-.*` (a gRPC/Netty stack several minor versions behind). Left in, those alone contribute a `critical` and 33 `high` advisories that no source change here can clear and that item 7's severity guard forbids ignoring, which would leave the gate permanently red and therefore permanently uninformative. The dividing line is remediability from this repo, not "is it tooling": `coreLibraryDesugaring` (bundled into the APK), `detekt*`/`ktfmt*` (pinned in the version catalog), and the Kotlin compiler classpaths all stay **in** scope. This deliberately **includes** the `*Test*` graphs, so the gate's coverage matches the objective's plain reading ("a Gradle dependency carrying a `high`+ advisory fails the PR") and matches the inventory channel it sits alongside; `testConfigs` is emptied so no component carries a `cdx:maven:package:test=true` stamp a downstream scanner could filter on. Record in a comment that a vulnerable test-only dependency therefore blocks a PR, and that narrowing to shipping-only would be a deliberate future change to §2, not a filter detail.
- [x] 3. Generate the SBOM locally and prove coverage by **set comparison, not by spot-checking coordinates**. For each configuration named in item 2, resolve its coordinate list independently (`./gradlew :<module>:dependencies --configuration <name>`) and assert the BOM's component set is a superset of the union. Coordinate *presence* cannot prove which configuration contributed — `ktor-client-darwin` is declared once in `iosMain` and so appears via all three iOS targets, `ktor-client-mock` is declared in `commonTest` and feeds every test graph, and the Compose libraries are `implementation` dependencies present in both debug and release graphs — so a generator could drop a whole target and still satisfy every name check. Assert separately that the two exclusion classes actually took effect, with a distinct witness for each: `com.android.tools.build:gradle` **absent** (it resolves only on the buildscript classpath) proves the `^classpath$` layer, and `org.bouncycastle:bcprov-jdk18on` / `io.netty:netty-codec` / `io.grpc:grpc-netty` **absent** proves the `androidLintTool` and `unified-test-platform-.*` layers — a witness that would still be present if only the buildscript filter were applied. This is also the item that proves the KMP native configurations resolve at all; if one cannot resolve on a non-Mac host, narrow the scope here and record exactly what was dropped and why.
- [x] 4. Choose the SBOM output path and prove `osv-scanner` 2.4.0 parses it. The file must land under a gitignored build directory (it is a build artifact, never committed), which means the existing `osv-scanner scan source --recursive .` will **not** see it — `build/` and `**/build/` are gitignored and osv-scanner honours `.gitignore` by default. Resolve this deliberately: name the SBOM's own path as the scan target rather than the repo root, and confirm the filename matches a name the CycloneDX extractor recognises. Target the **file**, not its directory: the generator has no output-format switch (`jsonOutput` and `xmlOutput` are separate properties, both always written), so `bom.xml` always sits beside `bom.json` with identical content and a directory target would extract both and double every package count. Keep `--no-ignore` so the command stays correct for a path inside the gitignored build tree. Do not use the deprecated `--sbom` flag.
- [x] 5. Make the scan **fail-closed**, and make it a single reusable scan-and-assert path (`scripts/scan-sbom.sh <sbom>`) so item 6's fixture goes through the identical command, config, and assertions — if the two paths can diverge, the fixture proves nothing about the path that actually guards pull requests. It must not pass `--allow-no-lockfiles`: that flag's whole purpose is to let a source-less scan pass, which is precisely the failure this gate must not have. Assert that the SBOM exists, that the report parses, that exactly one source was scanned, and that a non-zero package count came back, so a generator that silently emits an empty BOM turns the job red instead of green. Distinct exit codes (0 clean / 1 advisory matched / 2 not trustworthy) are required so item 6 can assert its fixture failed *because of the advisory* rather than because the scan never happened. The flag itself leaves `.github/workflows/security.yml` with item 8, which replaces that step wholesale — the two are coupled, since dropping the flag from the current repo-root scan makes it exit 128 immediately, and pointing the step at the SBOM before item 8 adds the generation step is the same failure; either would leave the branch's own required check red for three commits while proving nothing extra.
- [x] 6. Commit a **vulnerable-SBOM fixture** and a CI step that scans it through the exact same command and assertion path as the real SBOM, expecting a non-zero exit. This is the permanent regression guard: the real dependency graph is clean today, so without it every check still passes if a later edit stops invoking the scanner, points it at the wrong artifact, or drops the config. It is the same posture as the repo's `semgrep --test` fixture. The fixture's advisory must not be suppressible by `osv-scanner.toml` — verify the ignore list does not cover it.
- [x] 7. Add a **severity-policy guard** so the ignore list cannot be used to wave through the advisories this gate exists to block: fail if any `[[IgnoredVulns]]` entry in `osv-scanner.toml` names an advisory rated `high` or `critical`. Without it, §2's threshold is enforced by reviewer discipline alone — a later entry silences a critical advisory and the scan still goes green. Enforce it mechanically, matching `checkNoDetektBaseline` / `verifyKtfmtAlignment` / `verifyCheckPartition`. It must also reject `[[PackageOverrides]]` with `ignore = true`: measured against the committed fixture, one such block drops a `critical` match and takes the scan from exit 1 to exit 0, so a guard over `[[IgnoredVulns]]` alone has a one-line bypass — and since that form names no advisory, there is nothing to rate and it is rejected outright rather than thresholded. Severity comes from the OSV API (`database_specific.severity`), and every case where a rating cannot be established — unknown id, unreachable API, unrecognised rating — fails closed. Because it reads the network it lands as `scripts/check-ignore-severity.sh` run by the `sca` job rather than a Gradle task inside `check`: the local gate must not depend on reaching an external API, and it guards a file no Gradle task consumes. That is the same shape as `scripts/check-action-pins.sh` guarding the workflows' action pins.
- [x] 8. Wire SBOM generation, both scans (real + fixture), and item 7's severity guard into the **existing `sca` job** in `.github/workflows/security.yml`: add `actions/setup-java` and `gradle/actions/setup-gradle` steps reusing the SHA pins already present in this repo (no new action, so `actions-pin` stays satisfied). The job's name must stay exactly `sca` — `sca` is already a required status check in the `main` branch ruleset, and a rename or a split into a new job would leave the new check unrequired and therefore non-blocking on merge, satisfying every CI observation in this plan while failing §2. Keep the job on `pull_request` **and** `push`, and keep checkout at `submodules: false` — confirm nothing on the SBOM path reads the `docs/astro-docs` mirror.
- [x] 9. Confirm the gate is genuinely blocking end-to-end: temporarily pin one product dependency to a version carrying a known `high`+ advisory, confirm the `sca` job fails naming it, then revert. This is supplemental evidence on top of item 6's committed fixture — it exercises the real generator, which the fixture deliberately bypasses.
- [x] 10. Reconcile the sub-`high` policy against the real resolved graph: for each advisory below `high` with no patched parent, add a documented `[[IgnoredVulns]]` entry naming the coordinate and why it routes to the Renovate `osvVulnerabilityAlerts` baseline. If the graph is clean, add none and leave the list empty. **One entry already landed with item 6**: the resolved graph is not clean — `io.opentelemetry:opentelemetry-api@1.41.0` carries GHSA-rcgg-9c38-7xpx (MODERATE, CVSS 5.3) transitively via `org.jetbrains.kotlin:swift-export-embeddable`, with no patched parent. It had to be reconciled there because items 6 and 8 both require the real scan to PASS, which it could not while that advisory matched. This item is therefore a re-confirmation over the final graph plus item 7's guard, not a first pass over an empty list.
- [x] 11. Verify — and keep verifying — that `dependency-submission` is **retained** as the post-merge inventory channel, since §3 requires it and nothing else in this branch touches it. Assert statically that the job still exists with its `if: github.event_name == 'push'` condition, its `contents: write` permission, its SHA-pinned `gradle/actions/dependency-submission` step, and its `^classpath$` exclusion.
- [ ] 12. Correct the now-false prose asserting this job is dormant: the `sca` and `dependency-submission` comments in `.github/workflows/security.yml`, and the scope note in `osv-scanner.toml` — all three currently state the Gradle ecosystem commits no lockfile so osv-scanner never activates. State the new division: the SBOM scan is the PR-blocking gate; `dependency-submission` remains the post-merge Dependency Graph / Renovate inventory channel.
- [ ] 13. Update `.claude/CLAUDE.md`: describe the SBOM gate in the CI/Linting narrative, and confirm "Documented config files" names every file this branch changed (`gradle/libs.versions.toml`, `build.gradle.kts`, `.github/workflows/security.yml`, `osv-scanner.toml`, and the fixture).
